### 1b. `data/scores/` is destroyed on every run even once 1a is fixed

### 1c. The consistency guard has bypasses that must be closed before ⑤/⑧ publish

`src/report/consistency.py` is the mechanism CLAUDE.md's absolute rule 3 relies

checks ten and passes are the same verdict on the published page, an unrated

ticker's subject, and ordinary market prose (`매도 우위`) can drop the section
daily. **Registering `ANTHROPIC_API_KEY` before §2 F1 is fixed means the LLM
starts publishing directional prose over a guard with known holes.** The guard
fix should precede or accompany the key registration.

### 1d. The report filename disagrees with the session it describes

`reports/2026-08-28-evening.md` exists on 2026-08-27. The evening cron
(`37 12 * * 1-5`, 21:37 KST) fired ~10h late at 22:31Z 2026-08-27 = 07:31 KST

**reading** date, not the session. The same run writes `2026-08-27.parquet` and
`2026-08-28-evening.md`.

`report.yml`'s own comments (lines 124–131) document this exact defect from
2026-08-06 and guarded only the morning path against it. Consequences:
`reports/2026-08-27-evening.md` does not exist; a future evening cron on 2026-08-27
would overwrite `2026-08-28-evening.md`; and `src/eval/gate_2week.py`, which

This was a scheduler anomaly, not a routine one — the morning crons that day
also landed 221/281/311 min late (12:04 KST, three hours after the KOSPI open).
Normal scheduler lag over the two weeks was a steady 14–59 min. The three-times
morning cron (`report.yml`) defends against *dropped* runs, not against all
three being *delayed together*.

### 1e. Fixing the credentials still does not complete §2.2③

### HIGH

**F1 — `src/report/consistency.py` guard bypasses (four, one shape).**
Reproduced against real aliases with `ratings = {'005930': 매수, '000660': 약한 매도}`:

| input | `.ok` | `checked_lines` | note |
|---|---|---|---|
| `삼성전자는 SK하이닉스와 달리 강한 매도다` | `True` | 0 | comparative sentence — `v1_synthesis.md` asks for exactly this shape |
| `### 005930 삼성전자` / blank / `강한 매도 의견이다` | `True` | 0 | blank line clears `subject` (consistency.py:200-201) |
| `...NVDA 급락...강한 매도 압력...` after a 005930 line | `False`, wrong ticker | 2 | `_tickers_in` returns `()` for NVDA → label attributed to 005930 |
| `외국인 매도 우위가 이어졌다` | `False` | 1 | false positive — drops the section for ordinary prose |
| `지금이 저가매수 구간이다` | `True` | 0 | compound `저가매수` invisible to the matcher (also `분할매수`, `추격매수`) |

Root causes: (a) `ok = not self.contradictions` (consistency.py:102-104) makes
"checked nothing" indistinguishable from "checked and passed"; `render.py`
never reads `.checked_lines` or `.ambiguous`. (b) an unresolvable ticker neither
sets nor clears `subject`, so the label silently inherits the previous ticker.
(c) `rate_all` returning `{}` (any run where `kr_flow` fails, `render.py:799-800`)
makes the guard unable to fire at all. (d) the compound-Hangul exclusion in the
matcher regex (consistency.py:52) correctly kills `순매수/과매수/매도호가` but also
kills directional recommendations built the same way.

**F2 — `calendar` collector mints a spurious `-vN` of every event file every run.**
`src/collectors/calendar.py` stamps `known_at = now` on every row; `_differs`
(`scripts/collect_daily.py:200`) compares `known_at_utc`, so content that is
byte-identical always "differs". `data/raw/calendar/` holds 152 files, 133 of
them `-vN`, a perfect arithmetic progression `-v2` … `-v8` (19 each). `render()`
re-reads all 152 every run. Absolute rule 1 forbids deleting the existing
files; the fix is to stop the cause (exclude `known_at_utc` from `_differs`).

**F3 — `_differs` mis-compares datetime columns containing `NaT`.**
Same function. `check_dtype=False` neutralises the parquet `datetime64[s]→[ms]`
round trip *until* a `NaT` appears, then it falls back to int64 and every
non-null cell reads as 1000× different. `us_filings.report_date` is 93% null by
design → 14 of 21 files in `data/raw/us/filings/` are spurious, and the three
stored versions are provably identical.

**F4 — `kr_filings` aborts wholesale on any filing dated on a KRX-closed business day.**
`src/collectors/kr_filings.py:190` calls `session_close_utc("KR", d.date())`,
which raises `NoSessionFoundError` on a non-session day. DART accepts filings on
KRX closures (연말 휴장일 above all). `NoSessionFoundError` is not a
`requests.RequestException`, so it escapes `fetch`. For `backfill_kr_filings`
(`_KR_CHUNK_DAYS = 365`) every chunk of a 3-year window contains one year-end
closure — **the KR filings backfill cannot complete.** `us_filings._parse` has
the same shape on its `acceptanceDateTime`-absent fallback (Good Friday: EDGAR
open, NYSE closed) — lower severity, defensive branch only.

### MEDIUM

**F5 — the shadow portfolio buys tickers the briefing refused to rate.**
`src/eval/shadow_portfolio.py:82` selects `nlargest(size, "score")`. `rate()`
returns the raw `score` even when `low_confidence` forces 관망 (`rating.py:216`
buckets the label, not the score), and that score is the most inflated because
`score = raw / coverage`. Verified: `2026-08-06 035420 관망 score +1.468
coverage 0.409` sat at the largest weight in that session's top-7 basket. §8.5's
3-month gate reads this P&L. Currently outside the pinned window so no published
metric is affected yet.

**F6 — check #4 (hardcoded known value) never runs on live data anywhere.**
Every collector passes `known_value=False`. Correct for the 8-day daily window
(2024-01-02 out of range), but `backfill.py` uses the same `fetch()` and its
window *does* contain the pinned dates — so the one place `check_known_value`
would exercise is the one place it is off. The guard against "pykrx/Tiingo/FRED
restated 2024-01-02" has only ever run against committed fixtures, which cannot
restate.

**F7 — `_differs` / `_bucket` / `load_news_polarity_frame` smaller defects.**
- `bucket_from_score(nan, ...)` returns `약한 매도` with `low_confidence=False`
  (`rating.py:114-123`). Live path is protected; `rating_calibration.py:187-192`
  calls it on archived scores with no `dropna`.
- `load_news_polarity_frame` globs `scores/*.jsonl` with no `model_id` filter
  (`daily_scoring.py:224`), then de-dups keeping one row *per model* — an
  article scored by two models double-counts into `news_polarity`.
- `kr_price` / `kr_index` missing-ratio thresholds are unreachable: the
  non-nullable `int64` cast raises `IntCastingNaNError` before validation, so a
  partial bar surfaces as an uncaught crash, not the per-column check CLAUDE.md
  asks for. `kr_flow` avoided this with nullable `Int64` and documented why
  (`kr_flow.py:96-101`); the other two did not follow.
- `check_flow_identity` passes an all-null flow row (`sum(axis=1)` skipna,
  `kr_flow.py:221`). Mitigated because `missing_ratio` catches the same row.
- `backfill.py --revise` crashes with `min([])` on a fully-backfilled source
  (`backfill.py:136-139`) — the exact case the flag exists for.
- `check_trading_day_continuity` reports 40 missing sessions for 454910
  (mid-window listing) on every full-window validation, forever.
- `adapter.py:236` sends `temperature=None` rather than omitting the key;
  litellm absorbs it today but the adapter docstring and `bakeoff.py`'s
  `candidate_settings` both say it should be omitted.
- `calendar.py:403-405` `_parse_fomc_row` raises `ValueError` on a date cell
  with no `-` and no `(notation vote)` suffix (`int("")`). Not on the 2021-2027
  page it was verified against, so Low — but `_fetch_fomc_rows` catches only
  `requests.RequestException`, so it would drop the whole FOMC source.
- `gate_2week.py:140` parses the `kr_price/schema×31` occurrence multiplier into
  `FailureItem` and then `criterion_2` / the report body count `len(...)` —
  item count, not occurrences. Pass/fail direction is unaffected (zero vs
  nonzero), but the number read at the gate is understated.
- `kr_news.py:175-203` `check_collection_gap` takes a `df` it never reads —
  cosmetic, delete so the signature matches "did *this collector* run often
  enough".

**F8 — production scoring has no checkpoint before the full backlog finishes.**
`config/models.yaml` says `batch: true`, but the production path does not submit
a vendor batch. `daily_scoring.py` calls candidates sequentially, holds every
successful record in memory, and writes once after the loop. The current
four-day resolved backlog is 587 pairs; the stored gpt-5.4 bake-off latency
averages about 1.6 seconds/call, roughly 15.6 minutes before collector time.
`report.yml` gives the whole job 30 minutes. If a cold sync, API slowdown, or
runner cancellation lands before the final append, completed paid calls leave no
checkpoint and the next run repeats them. Incremental append or bounded chunks
cost more file I/O but make the archive's idempotency claim true under the
workflow's actual failure mode.

**F9 — §2.2③ is still a pre-scoring fallback, despite the producer existing.**
`render_news()` reports raw resolved counts and the first headline. It does not
consume relevance/polarity/uncertainty/intensity, choose the maximum-intensity
article, or deduplicate. This is documentation drift and a product gap: the
section title says news aggregation, but the displayed evidence is mention
volume only. Credential wiring alone cannot close it; see §1e.

## 4. Direction

**The approach is sound. No pivot.** Three reasons it has earned that:

1. **Determinism-first plus pre-registration has paid off, visibly and against
   interest.** The 2026-08-13 `forwardness` re-label check *failed* (0.30 >
   0.25) and the failure was left standing rather than the threshold moved or
   the passing sub-statistic substituted. §R holds a dozen corrections against
   interest. This discipline is what makes the 3-month gate result trustworthy.
2. **Training-data contamination is structurally avoided.** The news corpus
   accumulates forward from 2026-08-03, so every evaluated article post-dates
   every candidate model's cutoff — the dominant failure mode in published LLM
   trading work, avoided because there was no archive to be tempted by.
3. **Cost is in tolerance.** Measured: ⑤/⑧ are two calls of ~15KB × 2 runs/day
   ≈ under $5/month on Sonnet; scoring is gpt-5.4 at ~77% of a 250K/day free
   pool, ≈ $0. Under Ricky's stated ~$5/mo comfort line.

**Four caveats to carry forward:**

**(a) Time is one-directional, but the news archive is not lost.**
`_MIN_PERIODS = {"news_polarity": 60}` means 60 KRX sessions of scored news
before `news_polarity_z` is real — roughly the 3-month gate date (2026-11-13)
if scoring starts now. But `data/raw/kr/news/` is committed, so **the scoring
can be backfilled** over the ~25 days already collected (~3,500 calls, a few
days inside the free pool). Unlike RSS buffer loss, this is recoverable — it
just needs someone to run it deliberately.

**(b) The composite-input freeze held by luck, not design.** The 60-session
requirement means `news_polarity` cannot enter the ⑥ composite before the
3-month gate — which happens to avoid the "composite changed mid-evaluation"
failure PREREGISTRATION §8.4 guards against. This is fortunate, not planned;
the weight-activation decision should be explicitly pinned to *after* the
3-month gate and logged in §R when made.

**(c) The one unvalidated half of the 2-week gate is "does a human read it."**
33 briefings shipped; the trial log's `읽었나` is `기록 없음` or `아니오`
throughout. Ricky's hold was reasonable while ⑤/⑧ were absent — but its cost
was that 1a/1b sat unnoticed for three days. The system's design premise is a
human reading and acting. That is the one thing the 2-week window could measure
that is not a signal question, and it is the one that came back unanswered.

**(d) Collection and report timeliness are now different infrastructure
questions.** The 2026-08-07 decision to leave news collection on GitHub Actions
still holds: low declared-run coverage produced little realised RSS loss, and a
new host would add credentials, deployment, and monitoring. The report product
has a different requirement — a pre-open briefing delivered before the open.
On 2026-08-27 all three morning crons were delayed together by 221/281/311
minutes and the evening cron by 594 minutes, evidence against the workflow
comment's assumption that duplicate crons are independent draws. Do not move
collection. If correlated multi-hour delays recur, reconsider only the
twice-daily report trigger on a cheap persistent scheduler.
