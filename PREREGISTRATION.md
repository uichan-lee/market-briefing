## 8.1 What can and can't be validated in weeks 1–2

| Validation target | Feasible in 2 weeks? |

| Pipeline integrity (missing data, duplicates, delays) | ✅ |
| Data consistency (cross-check against source) | ✅ |
| Entity-matching accuracy (`ambiguous` ratio) | ✅ |
| LLM output reproducibility | ✅ |
| Model performance vs. golden set | ✅ |
| **Inter-model agreement** | ✅ |
| Measured cost | ✅ |
| Whether the briefing actually gets read | ✅ |
| **Signal hit rate** | ❌ |
| **Strategy profitability** | ❌ |

## 8.2 Why hit rate isn't feasible

Distinguishing a directional hit rate of 55% from 50% ($\alpha=0.05$, power 0.8) requires roughly **800** independent observations. 30 tickers × 10 trading days = 300 observations, and tickers on the same day are strongly correlated via market beta, so the effective sample size is roughly 1/3 to 1/5 of the nominal count — effectively 60–100 observations. That's not enough to determine anything.

Strategy-level evaluation is even worse. Making an annualized Sharpe of 1.0 significant at $t=2$ requires roughly 4 years of data.

**Consequence, stated in advance:** any hit-rate number produced during the first two weeks is noise and will not be reported as evidence, in either direction. A flattering early number is not a reason to continue, and an unflattering one is not a reason to stop.

## 8.3 What gets measured in 2 weeks instead: inter-model agreement

> [!tip] The core idea
> We can't measure predictive accuracy yet, but we **can** measure measurement stability. Run the same articles through 3 different models and look at the score correlations.
>
> - **High agreement** → at minimum, whatever we're measuring is a real underlying signal. Predictive power still needs to be validated separately.
> - **Low agreement** → the scores are model-specific noise. Not yet eligible to move on to predictive-power validation. Fix the schema or the prompt first.
>
> This only needs a few hundred articles, so 2 weeks is plenty. And this diagnostic tells us far more than a meaningless number like "55% hit rate" would.

Measurement: per-dimension Spearman correlation for each pair of candidate models. Warn if the `polarity` correlation falls below 0.5.

### "LLM output reproducibility", operationally

§8.1 lists this as measurable in two weeks. It is defined here rather than there because §8.3's subject is measurement stability, and stability *within* one model is the other half of stability *between* models — same idea, one axis apart.

Written on 2026-08-11, before the bake-off has run, for the reason the other two operational definitions in this document were: **a criterion with no referent acquires one at the moment somebody needs a verdict.** This is the third such term, after "runs without interruption" and "zero data-consistency errors".

**Reproducibility is read as the same conclusion, not the same output.** Byte-identical scores were never available — SPEC §6.1 has said since v0.1 that *"even at `temperature=0`, the LLM isn't perfectly identical run to run"* — and as of 2026-08-11 `temperature` cannot be pinned across vendors at all (SPEC §6.3). So the question is whether re-scoring the same article moves it enough to change what the pipeline concludes from it.

- **Instrument:** the per-dimension standard deviation across the §7.4 bake-off's 5 repeats of each article.
- **Corpus:** the 100 golden-set examples, which is what the repeats are run over.
- **Threshold:** SPEC §7.4's existing `polarity σ < 0.1`. No new number is introduced here.
- **Reported with:** the temperature each model was actually sent. Candidates given different values were not run under identical conditions, and the bake-off table prints the column so that fact is visible rather than inferred.

**This is not a §8.5 gate criterion, and none is being added.** The four criteria at the 2-week gate — runs without interruption, zero data-consistency errors, `ambiguous` < 30%, inter-model polarity correlation > 0.5 — are unchanged. This section gives a §8.1 row a meaning it lacked; it does not give it teeth it never had.

**Pipeline-level reproducibility is a separate mechanism.** Whether a re-run reproduces a *published* rating depends on archiving scores, not on re-scoring: SPEC §3 specifies `data/scores/{date}__{model_id}__{prompt_version}.jsonl`. When this paragraph was written that directory was not excepted in `.gitignore` and the production scoring stage did not exist.

**[Update, recorded in §R 2026-08-27]** The archive and the scoring stage were **built and wired** — `src/llm/daily_scoring.py`, registered in both runs of `scripts/collect_daily.py`, and `.gitignore` now excepts `data/scores/`. Two gaps remain and are documented in the §R row: `report.yml` passes no `OPENAI_API_KEY` and does not stage `data/scores/`, so the stage has not run in production and no archive exists yet. The principle is unchanged: **deferring a measurement is legitimate, quietly dropping it is not** — and this stays a §8.1 reproducibility target, not a §8.5 gate criterion.

**[Update, §R 2026-08-29]** Both gaps are closed. `report.yml` now carries `OPENAI_API_KEY` and stages `data/scores/`, Ricky registered the Actions secret, and the manual `report.yml` run of 2026-08-29 (evening, Actions run `33243653416`) produced and committed `data/scores/2026-08-29__gpt-5.4__v1.jsonl` (536 scored pairs). The archive now exists and grows one file per run; this remains a §8.1 reproducibility target, not a §8.5 gate criterion.

## 8.4 Signal evaluation design (after 3 months)

**Evaluate on excess return, not absolute direction.**

$$y_{i,t+1} = r_{i,t+1} - r_{\text{sector}(i),t+1}$$

Removing market beta sharply reduces cross-ticker correlation, which rescues the effective sample size. The evaluation metrics are not hit rate but:

- **IC (Information Coefficient)**: Spearman correlation between score and next-day excess return, logged as a daily time series
- **ICIR**: mean IC ÷ stdev of IC
- **Quantile spread**: excess return of top-20%-score bucket − bottom-20%-score bucket

**Which "score" is evaluated.** Both, reported separately and never pooled:

1. The **composite rating score** from SPEC §2.2⑥ — the continuous value, not the seven-point bucket. This is the pipeline's actual output and the thing the shadow portfolio trades.
2. The **news polarity score** from SPEC §6.2, aggregated per ticker — retained as a component-level diagnostic. If the composite carries signal while its news component does not, the LLM stage is decoration and should be cut.

The continuous composite is what enters IC, not the bucket label. Bucketing discards information and its cut points are a display choice; correlating on the label would confound the signal's quality with the arbitrariness of where the thresholds sit.

**Cut points are frozen against outcome data.** The seven-point thresholds in SPEC §2.2⑥ may be adjusted for distributional reasons — for example if 95% of tickers land in `관망`, making the scale useless — but never because a different cut would have produced better-looking returns. Any change is logged in §R with which of those two reasons applied.

**What the composite contains.** As of the v0.5 revision the composite includes medium-term per-ticker features (`rel_strength_120d`, `flow_persistence_60d`, `rev_trend_12w`) alongside the original short-horizon set. The metric is unchanged; the input is not, and that distinction is exactly what a pre-registration exists to record. This was fixed before any collector ran.

**Evaluation-window composite freeze, clarified 2026-08-27.** The implemented
composite for the 2026-08-13 → 2026-11-13 window is the active mapping in
`config/rating.yaml`: `foreign_flow_5d`, `inst_flow_5d`, `rel_strength_20d`,
`short_ratio`, and `valuation_band`, total absolute weight 0.75. The medium-term
features named in the v0.5 design paragraph above were never implemented or
weighted; `rev_4w` was permanently dropped; and `news_polarity` remains in
`deferred_weights`. None may enter the composite before the 3-month gate is
read. Activating `news_polarity` earlier would mix two score definitions inside
one evaluation window; the alternatives would be to keep the current composite
or restart the clock. The fixed decision is to keep the current composite and
consider activation only after 2026-11-13, with a new §R entry.

**The macro regime layer is excluded from the composite, on measurement grounds.** SPEC §2.2⑨ indicators are common to every ticker on a given day. Since the evaluation target above is *sector-excess* return, a common term cancels by construction — it can add variance to the composite but cannot contribute IC. Folding macro into a per-ticker score would therefore degrade a measurement while appearing to enrich it. The regime is reported as its own section and evaluated, if at all, as a separate question.

**SPEC §2.2⑧ commentary is outside evaluation entirely.** It enters no IC, no ICIR, no quantile spread, and no shadow portfolio position. It is LLM-authored prose and therefore not reproducible; admitting it to the evaluation path would make the results depend on a model version and a sampling temperature. It is checked for consistency against the rating (`src/report/consistency.py`) and otherwise treated as a display artifact. Whether it is *useful* is a format question, measured in the trial log at MANUAL-TASKS §8, not a signal question.

## 8.5 Decision gates

| Checkpoint | Criteria | If not met |
|---|---|---|
| 2 weeks (2026-08-12 → 2026-08-26) | Pipeline runs without interruption, zero data-consistency errors — both defined below — `ambiguous` < 30%, inter-model polarity correlation > 0.5 | Halt signal work, repair the measurement layer |
| 3 months | ICIR > 0.3, shadow portfolio beats KODEX 200 buy-and-hold | Discard the signal logic and redesign |
| 6 months | Above conditions hold even after accounting for transaction costs (fees + transaction tax + slippage) | End the project, switch to indexing |

**Any real-money trading, even small amounts, only begins after passing the 3-month gate.** Changing trading behavior based on 1–2 week results means chasing noise.

### The 2-week clock: starts 2026-08-12 00:00 UTC, read 2026-08-26

The clock does not start from the first collector run (2026-08-03) or the first unattended scheduled run (2026-08-06), because continuity over those days is not merely unmeasured — it is unmeasurable. Until 2026-08-10 a run that polled and found nothing new wrote no file, so "GitHub did not fire" and "the run fired and the feeds were quiet" are the same absence in the stored record. Two fixes closed that on 2026-08-10, one in `kr_news.main()` and one in `collect_daily.collect_news`.

**The clock was pinned to 2026-08-11 and moved one day on 2026-08-11**, because `check_feed_continuity` changed on that date and a window has to be measured under one definition of its own criterion. The window had elapsed roughly an hour and held zero runs when the change was made, so nothing measured was discarded. 2026-08-12 is the first full UTC day under the current check.

### "Runs without interruption", operationally

Three conditions, over the window, all of them about what this pipeline controls:

1. **Every run that fires records a run file** under `data/raw/kr/news/`. This is now an invariant of both callers rather than an observation, so a violation means a code defect, not a quiet hour.
2. **No `check_feed_continuity` failure is left unexplained.** A feed that did not answer is recorded together with what its silence cost — an unverified feed is an acceptable event; an unverified feed nobody sized is not. Since 2026-08-11 the check itself supplies the sizing: the outage is reported every run and the next run that answers measures what it cost, so a failure here now means either a measured loss or a feed silent past `MAX_FEED_SILENCE` (24h), where no later run can settle it.
3. **No two consecutive runs fail validation for the same cause.**

**Delivered-run coverage is measured and reported with the gate decision, but is not itself a criterion.** GitHub's scheduler drops a large share of declared cron runs — 42.6% hourly coverage over 2026-08-03..07, and 105 stored run files across 2026-08-03..10 against 31 declared runs a day. That loss is real and is reported, but it originates outside the pipeline, and gating on it would fail this project's measurement layer for someone else's defect. What the gate asks is whether the runs that happened lost anything.

Calibration, stated so the threshold cannot be chosen later to fit an outcome. The five consecutive failures of 2026-08-08 fail condition 3: their cause was a real defect in how the run clock was read, and it took five runs and a code change to stop. The transient feed outages of 2026-08-10 and 2026-08-11 do not, and after the 2026-08-11 change they are no longer validation failures at all — including the three consecutive ones between 03:05 and 07:58 KST that day, which is why the change was made before the window opened rather than after a gate reading. `tests/test_kr_news.py::test_the_2026_08_11_alarms_would_not_fire_now` replays all five of those runs from the Actions log and holds this statement in code.

The distinction the two sides of that calibration draw: **condition 3 counts causes the pipeline can fix, not weather it runs in.** A run clock read from the wrong field is the first. A Korean publisher refusing connections from a US-hosted runner is the second.

### "Zero data-consistency errors", operationally

A data-consistency error is **data that arrived and contradicts itself or another source.** Not data that failed to arrive — that is the criterion above — and not data that arrived incomplete.

The codebase has no severity field and no category tag: `CheckResult` carries `name`, `passed`, `detail`, and `ValidationReport.ok` is a flat conjunction. So the criterion is an explicit allowlist of checks, which is workable because the name space is small and closed. Four entries, and all four run on live data:

| Check | Where | What contradicts what |
|---|---|---|
| `schema` | `validate.py:check_schema` | Column names or dtypes differ from the declared contract |
| `structural_invariants` | `kr_news.py` | Future timestamps, link host against its feed's domain, duplicate `article_id`. **Article age is excluded — see below.** |
| `flow_identity` | `kr_flow.py` | The accounting identity — four investor net-buy columns summing to zero — fails, which means the columns are mis-mapped |
| Vendor disagreement | `render.py:merge_us_preview`, `VENDOR_TOLERANCE = 0.001` | Alpaca and Tiingo state closes more than 0.1% apart for the same session |

**What is excluded, and why, written before the window opens:**

- `missing_ratio` — completeness, not contradiction. The only failure on record (2026-08-06, `kr_flow` `short_balance` missing 42.9%) is the short-sale disclosure lag that `SHORT_LAG_SESSIONS = 3` exists for. Nothing disagreed with anything.
- `trading_day_continuity` — on 2026-08-06 morning, 25 of these failed at once and all 25 were fallout from a single Tiingo `rate_limit`. Counting by check name would book one availability incident as 25 consistency errors.
- `fetch`, `not_empty`, `collection_gap`, `feed_continuity`, `rate_limit`, `krx_session`, `crash` — availability, already covered by the criterion above.
- `coverage` (macro) — mixed, so it is split explicitly. Its observed failure mode is availability (the window opening after the series' last observation, 2026-08-10) and is excluded. But two of its sub-conditions — **rows dated to weekends** and **duplicated dates** — are contradictions, so a `coverage` failure whose `detail` names either of those counts.
- `structural_invariants` (`kr_news`) — mixed, and split the same way `coverage` is, for the same reason. Three of its four sub-conditions are contradictions and count: **future timestamps**, **a link whose host does not match its feed's domain**, and a **duplicated `article_id`**. The fourth, **an article older than `_OLDEST_PLAUSIBLE` (30d)**, is excluded: it is a freshness heuristic, not a contradiction. An outlet re-publishing an old item into its RSS buffer produces an article that is accurately parsed and honestly timestamped, and it disagrees with nothing — the check is doing its job by reporting it, and §8.1 glosses this criterion as "cross-check against source", which an old date is not. The remaining three stay because each of them means the data is *wrong*: a future timestamp breaks the look-ahead boundary, a foreign host means the article was attributed to the wrong outlet, and a duplicate id means dedup silently dropped something.
- `known_value` and `implied_close` — these are the purest cross-source checks in the system, and **they do not run on live data at all.** Both pin a specific historical row (2024-01-02), so every `fetch()` passes `known_value=False` and they execute only during backfill and tests. This is recorded because §8.1 glosses this criterion as "cross-check against source", which is exactly these two: their clean record over the window must not be read as evidence that cross-checking passed.

**Where it is read.** From the committed report headers in `reports/` — the `⚠ 수집 실패: <collector>/<check>` and `⚠ 미국 시세 벤더 불일치` lines — over the window's 10 KRX sessions, at most 20 reports. Not from `data/status/`: that directory is gitignored as a per-run handoff, `read_status` deliberately reads only the newest file, and no range aggregation over it exists. The hourly `collect-news` runs do not call `write_status` and so never reach a report header; for those, the window's Actions run conclusions are the record, which covers a two-week window at 90-day retention but is not a permanent artifact.

**Calibration, fixed in advance.** Over the whole record to date (2026-08-03..10, six reports) this definition counts **zero**. `flow_identity`, `schema` and the vendor comparison have never failed; the header failures on record are `kr_flow/missing_ratio` twice, `kr_news/fetch` twice and `macro/coverage` once, all excluded above. A broader definition would open the window already holding two, which would force a tolerance to be chosen — after the count was known.

**The `structural_invariants` split was calibrated against two real failures, and the count is stated rather than implied.** On 2026-08-11 the hourly runs failed this check twice — run `31452565324` at 02:30Z on an article dated 2026-03-09, and run `31461852496` at 05:30Z on one dated 2025-11-21 — two of the eight runs that day. Both were the age condition alone; the other three sub-conditions have never fired, on any run. Under the check-name allowlist as written on 2026-08-10 those two would have counted, and at that base rate the window would have opened holding a criterion it was going to fail on outlets re-publishing their own archives. **Under the split above the record still counts zero, and it counts zero for a stated reason rather than because the failures had not happened yet.** The split is written before the window opens, which is the only ordering under which it is a definition rather than an adjustment; that the failures were already visible is recorded in §R.

### What is evaluated, operationally

**The forward return is not close-to-close.** §8.4 writes the target as $y_{i,t+1} = r_{i,t+1} - r_{\text{sector}(i),t+1}$ without fixing where $r$ is measured. It is fixed here as

$$r_{i,t+1} = \frac{\text{close}(t{+}1)}{\text{open}(t{+}1)} - 1$$

because the evening run publishes at 21:37 KST, **six hours after the 15:30 close of session $t$**. A close-to-close return enters at a price that existed before the rating did. That is look-ahead — the same class of defect this project prohibits everywhere else, and the one it corrected in `short_ratio` on the morning this was written. Entering at the open of $t+1$ is the earliest moment the signal could actually be acted on. The cost is that the overnight gap is not captured, which is honest: it is not capturable.

This is a departure from the plain reading of §8.4 and is recorded as one in §R rather than presented as an interpretation.

**Singleton sectors take the universe return.** Sector membership is the `sector:` field on each watchlist entry; five of the ten KR sectors currently hold exactly one ticker, and for those $r_{\text{sector}(i)} \equiv r_i$, making the excess return identically zero and `_sector_returns` correctly `NaN`. Those five tickers instead have the **equal-weighted 31-ticker universe return** subtracted. Leaving them out would shrink each session's cross-section from 31 to 26 for a reason that is a property of the sector table's shape rather than of the data, and §8.4's stated purpose for the sector term — removing market beta so the effective sample survives — is served by the universe return just as well.

### The shadow portfolio, operationally

§8.5 said "beats KODEX 200 buy-and-hold" and nothing else; nothing in the repository defined what the portfolio held. Fixed here:

| | |
|---|---|
| Universe | the 31 KR tickers in `config/watchlist.yaml` |
| Selection | top 20% by composite score each session — `ceil(31 × 0.2)` = **7 names** |
| Weighting | equal, long-only, no cash, leverage 1.0 |
| Rebalance | every session, executed at the **open of $t+1$**, matching the return convention above |
| Sessions with no published rating | **hold the previous position** |
| Benchmark | 069500 (KODEX 200), buy-and-hold, same window, same execution convention |
| Costs | **zero** — fees, transaction tax and slippage are what §8.5's 6-month gate exists for |
| "Beats" | higher cumulative return over the window. Not risk-adjusted |

Long-only equal-weight against a long-only index keeps direction and leverage the same on both legs, which is what lets a plain return comparison mean something without a risk model. Holding through a missing rating follows the 2-week gate's treatment of dropped runs: GitHub's scheduler is not this pipeline, and a criterion should not turn on it.

### ICIR: the threshold does not move, the uncertainty is reported

The criterion stays `ICIR > 0.3` on the point estimate, exactly as pre-registered. Reported alongside it, and fixed here so it cannot be chosen later:

- a **bootstrap 95% confidence interval**, resampling the daily IC series 10,000 times with a fixed seed;
- the number of sessions that actually entered the series, which is not the same as 62;
- the plain fact that at ~60 sessions the standard error of ICIR is roughly $1/\sqrt{60} \approx 0.13$, so **0.3 sits about 2.3 standard errors from zero.** A point estimate that clears the bar with an interval straddling zero passes the gate as written and does not settle the question.

This adds no criterion and relaxes none. It exists so that the reading on 2026-11-13 cannot be more confident than the sample supports, in either direction.
